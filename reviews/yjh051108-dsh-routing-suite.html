I cloned yjh051108/dsh-routing-suite expecting a router and got something narrower and stranger. The repo packages two things that only make sense inside the DeepSeek dsh ecosystem: a runtime plugin injector called dsh-super-injector and a reasoning-mode routing preset called dsh-router-standard. The injector is the real code. Its job is to let you load arbitrary local plugin packages into a running dsh instance without editing patch/package.json, then hot-reload entire packages on file change. The preset side is mostly documentation and archived .mjs bootstrap files under preset/docs/archive/router-react/. The problem being solved is specific to dsh plugin authors who want BepInEx-style runtime surgery on a Windows PowerShell workflow.

Getting it running on our Linux box was not possible in the intended sense. The declared entry point is install.ps1, a PowerShell script that calls dsh plugin --profile web add .\injector. There is no top-level package.json, no pyproject.toml, no Cargo.toml. The actual source lives in injector/src/index.ts, a 3320-line TypeScript file that imports Context from cordis and types from @deepseek-ai/cordis-plugin-loader, @deepseek-ai/dsh-system-prompt, and @deepseek-ai/dsh-tools. None of those packages are vendored. The build config in injector/tsdown.config.ts bundles everything non-node: into lib/index.js specifically because, per a comment in that file, official assembly fails to resolve link: peer deps from out-of-tree paths and the whole plugin tree dies. The injector has its own package.json and lockfile, but no built lib/ directory ships in the repo. You would need a dsh checkout, Node, tsc or tsdown, and a Windows PowerShell host to actually install. Our run confirmed this: the documented usage is internally consistent but targets a toolchain we do not have.

When we executed our inspection script, the file tree output showed exactly what the repo contains. Beyond the .git directory, the real files are install.ps1 at the root, the injector/ subproject with its src/index.ts, src/client/index.ts, tsdown.config.ts, package.json, and scripts/build.sh, and the preset/ directory of markdown docs and archived router bootstrap files. We then ran node -e require('./index.js') against the source, which exited with code 1 because there is no built index.js at the repo root and the TypeScript entry imports packages that are not installed. That exit tells you plainly: this is source, not a runnable artifact, and it cannot run without its host ecosystem.

The architecture is visible in the code comments and exports. The injector defines five core capabilities: dev_inject_plugin for runtime injection via junction plus loader.create without persistence, dev_install_package for dual-path hot assembly that survives restart, dev_reload_package for deterministic full-package reload that clears cache and rebuilds the fiber with rollback on failure, dev_plugin_status for listing assembled plugins, and dev_injected_list backed by registry.json. A watch loop polls lib output fingerprints and triggers hot reload. The client UI in injector/src/client/index.ts is 167 lines that render a settings panel via SlotsService and talk to /super-injector/api with plain DOM element construction. The build produces two bundles: a browser CJS client wrapped in window.__ModuleLoader__.load and a Node ESM host bundle with zero non-node externals.

The quality picture from what we observed is mixed in a specific way. The code is detailed and clearly written by someone who hit real bugs: the tsdown.config.ts comment documents issue #1 where link: deps break plugin loading, and index.ts notes that official HMR does not work for bundle plugins because node_modules is excluded. There are zero test files and no CI. The MIT license is present. The 71 files across 3612 lines split into TypeScript and Shell with no automated verification is a real gap for something that does runtime patching. The repo has 6870 stars and is rising, which suggests an active dsh community, but nothing here is independently testable outside that host.

Anyone who actually uses dsh on Windows and writes Cordis plugins for it may find this useful for hot-reload development. Anyone else will clone it, find no runnable entry point, and stop. It bites if you expect a standalone router suite, because the preset is documentation and the injector is tightly coupled to @deepseek-ai/* internals that are never vendored or built in this repository.
