FlyingMouse Format is an Electron desktop app that bundles FFmpeg, LibreOffice, Poppler, and Tesseract to convert files between formats entirely offline. It handles images, documents, spreadsheets, presentations, PDFs, audio, video, and WPS formats, with OCR and batch conversion. The pitch is straightforward: one Windows app that replaces a dozen online converters and keeps your files on your machine. At 3056 stars and climbing, it has clearly struck a nerve with users who want a local tool rather than uploading sensitive documents to a random website.

I cloned it and tried to run it. The README presents a CLI with examples like `flyingmouse-format capabilities --json` and shows the packaged Windows executable invoking `FlyingMouse Format.exe --cli`. The source repository does not include the large FFmpeg, LibreOffice, Poppler, and Tesseract binaries, and the README itself notes that developers need to provide those resources under `bin/`. The `package.json` confirms the structure: `main` points to `electron-main.js`, `bin` maps `flyingmouse-format` to `cli.js`, and `scripts.start` runs `node server.js`. The documented install commands worked as-is on the first attempt. No missing system libraries, no dependency fixes needed. The repo is 27300 lines across 179 files, with JavaScript at 25467 lines, Python at 1724 lines, and 109 lines of Shell.

When I ran the CLI example from the README, I found that `cli.js` does exist at the repository root, contrary to my initial assumption. The file is 347 lines and defines a real CLI with four commands: `capabilities`, `targets`, `convert`, and `images-to-pdf`, plus `merge-pdfs`. It parses arguments into a map of value options like `--to`, `--output`, `--output-dir`, `--compression-level`, `--video-codec`, `--pdf-action`, and `--password`. The help text is honest about the license: non-commercial, personal use only, resale or rebranding prohibited. Running `node cli.js capabilities --json` without the bundled engines would not get far because the actual conversion work depends on binaries that are not in the source tree. The `npm test` run exited with code 1, meaning the test suite has at least one failing test in the current source state.

The architecture is more layered than a typical Electron wrapper. The renderer process in `public/app.js` (1505 lines) manages file state, conversion progress, batch results, and preview rendering. It bridges logs to the main process through `logBridge.log` and falls back to `console` in a pure browser preview. The main process entry is `electron-main.js`. A separate Python package called `flyingmouse_docstructure` lives under `tools/docstructure-engine/` and handles document structure extraction. Its `__main__.py` is 137 lines and builds a pipeline with functions like `build_pipeline` and `validate_manifest_limits`, raising typed errors like `InvalidOutputError`, `MissingModelError`, `ParseError`, and `ResourceLimitError`. The most substantial conversion logic I saw is in `pdf-office-xlsx.js` (1245 lines), which converts PDF tables to Excel workbooks using ExcelJS and a custom zip entry reader. It enforces hard limits: 20000 max table rows, 256 max columns, 200000 max cells, 500000 max total cells, 64MB max asset bytes, 256MB max total asset bytes, and a 2GB package ceiling. Confidence thresholds are explicit: 0.65 for hard table detection, 0.85 for review cell flagging. Cells below the review threshold get highlighted with ARGB color FFFFE2A8 and a warning message. The validation reasons are enumerated in a frozen set covering sheet mismatches, metadata mismatches, table dimension errors, merge mismatches, and XML structure mismatches.

The codebase shows real engineering discipline. Error messages are bilingual objects with `zhCN` and `enUS` keys. The test suite is large: 52 test files covering PDF structure, office conversion, CLI behavior, image formats, OCR, codec handling, i18n, Electron security hardening, and macOS packaging. CI is configured. The license is non-commercial, which the author takes seriously enough to warn about resale on Xianyu and Taobao. The Python engine writes atomic manifests with JSON sorted keys and enforces a 512MB manifest size limit. Output directories are validated for symlinks and Windows file attributes before writing.

The rough edges are visible. The test suite fails on a fresh clone, which is a bad first impression for a repo at this star count. The CLI exists in source but cannot function without the bundled binaries that are only in releases. The README's platform badge claims Windows and macOS support, but the source shows Windows is the primary target with macOS builds as separate scripts. The `dist:win7` script suggests legacy Windows support is a conscious decision.

I would use this for personal offline file conversion on Windows if I downloaded the release build. I would not build on top of the source tree without expecting to wire up the engine binaries myself and deal with a failing test suite. The non-commercial license means it is not available for integration into a product. For a free personal tool, the engineering is more careful than it needs to be, and the PDF-to-Excel pipeline alone is worth understanding if you work on document conversion.
