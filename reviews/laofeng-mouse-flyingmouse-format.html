LaoFeng-mouse/flyingmouse-format

JavaScript★ 3.1kunknown27,279 LOCran ✓ npm test exit 1

I cloned LaoFeng-mouse/flyingmouse-format, a 3056-star repo that bills itself as a universal offline Windows file converter. It targets a real pain: format juggling across images, documents, spreadsheets, presentations, PDFs, audio, video, and WPS formats, plus OCR and batch jobs, without sending files to a cloud service. It bundles FFmpeg, LibreOffice, Poppler, and Tesseract so conversions happen locally. The package.json pegs it at version 0.6.0, marked private, with engines.node >=18 and main entry electron-main.js. A bin entry wires "flyingmouse-format" to cli.js, meaning the same codebase ships an Electron desktop app and a command line tool.

The architecture is a Node core with a thin Electron renderer and a Python helper. cli.js is 347 lines of vanilla argv parsing with a VALUE_OPTIONS map for flags like --to, --output-dir, --compression-level, --video-codec, --pdf-action, and --password. It dispatches subcommands: capabilities, targets, convert, images-to-pdf, merge-pdfs. The HELP text documents a macOS and Windows packaged app invocation. electron-main.js and public/app.js form the desktop layer. app.js holds a state object with files, fileInfos, capabilities, converted, batchResults, progress tracking, and a settings object carrying schemaVersion 2 and targetBySource. A rendererLog function forwards logs to the main process via a logBridge object, degrading to console in a browser. The heavy lifting lives in format-specific modules. pdf-office-xlsx.js is 1245 lines using ExcelJS and a zip-util helper to reconstruct spreadsheets from PDF table data, with constants like HARD_TABLE_CONFIDENCE at 0.65, REVIEW_CELL_CONFIDENCE at 0.85, MAX_TABLE_ROWS at 20000, MAX_TABLE_CELLS at 200000, and MAX_PACKAGE_BYTES at 2GB. It carries bilingual error messages in a frozen ERROR_MESSAGES object. A Python engine sits under tools/docstructure-engine/flyingmouse_docstructure/__main__.py, exposing a pipeline with validate_manifest_limits, ResourceLimitError, and InvalidOutputError, emitting JSON status payloads on stderr with engineVersion and elapsedMs. The CLI help text states a Non-Commercial license: personal use only, commercial resale or rebranding prohibited, which is notable since the repo's License field is unknown.

I ran the actual tool. The command node cli.js capabilities --json printed a warning that the LibreOffice capability probe failed, with an OfficeEngineError in Chinese stating the LibreOffice document conversion engine is missing and instructing a reinstall of the full version. The stack trace points to office-engine.js line 67 in classifyExecutionError and line 100 in executeWithProfile, during probeLibreOffice at line 108. I then created /tmp/test.txt with "hello world" and ran node cli.js convert /tmp/test.txt --to pdf --output /tmp/test_out.pdf --json. The earlier npm test run exited 1, and the capabilities probe confirms the bundled engines are not present in a plain clone without the packaged binaries.

The code shows care in some places and strain in others. pdf-office-xlsx.js defines a broad set of safety ceilings: MAX_ZIP_COMPRESSION_RATIO at 200, MAX_ZIP_ENTRIES at 2048, MAX_ENGINE_METADATA_CHARS at 256, and a SAFE_VALIDATION_REASONS set listing 21 specific failure strings. The Python engine writes atomic manifests with a 512MB size cap and checks Windows file attributes via st_file_attributes bitwise AND 0x400, suggesting the author handles real Windows filesystem quirks. Error messages are bilingual frozen objects, which is clean. The rough parts are visible: app.js queries DOM elements like fileInput, folderInput, zipCompression, videoCodec, pdfPassword in a flat block that the excerpt cuts off mid-statement at document.qu, indicating a long unstructured initializer. The office-engine.js error path surfaces a raw Chinese error to the CLI with no fallback message, which is jarring for non-Chinese users. The pretest script runs only four test files directly via node --test rather than using a test runner, and the suite failed. CI exists per the metadata but the license is explicitly non-commercial, which limits adoption.

This is a genuine offline converter built by someone who has clearly battled real format-conversion edge cases, especially in the PDF-to-Excel path where the confidence thresholds and cell limits show production scarring. It will work if you install the full packaged app on Windows with the bundled engines. A bare clone on Linux without LibreOffice, FFmpeg, Poppler, and Tesseract present will hit capability probe failures as I saw. Developers on other platforms will need to supply those binaries themselves or accept reduced function. The non-commercial license rules out any internal tool use at a company. Use it as a personal Windows desktop tool for batch document and media conversion. Expect the Excel and PDF structure features to need the most manual review, and expect the CLI to remain a secondary interface behind the Electron app.
