Awesome DSH Plugin is a curated registry of plugins for DeepSeek Harness, the open source coding agent framework from DeepSeek. The problem it solves is cataloging the moving parts of a harness where "everything is a plugin" (models, tools, sandboxes, session storage, UI, and the agent loop itself) so that developers extending or replacing parts of the agent have a single place to find what exists. The repository is not itself a plugin runner; it is a data driven list plus the tooling that generates the READMEs and the accompanying site from per plugin YAML files.

Getting it running was straightforward for the one script I exercised. The documented usage of scripts/reorder-categories.py worked as written. I cloned into /tmp/rr/awesome-dsh-plugin_awesome-dsh-plugin, inspected the two files the script modifies, derived the current category order from scripts/lib/entries.mjs, and invoked the script with that order. No missing system libraries, no extra installs beyond python3 and node already on the box. The repo reports Python as its primary language but the meaningful code I touched was a 40 line Python script that shells out to a Node generator, so you need both interpreters present. CI is enabled and there are 10 test files, though I did not run the suite; the metadata notes an import failure in the suite, which I did not chase down because it was unrelated to the script I needed.

What actually happened: I ran python3 scripts/reorder-categories.py "$CURRENT" where $CURRENT was the existing CAT_IDS list, ui,usage,theme,model,session,memory,tools,browser,vision,voice,docs,skill,workflow,git,notify,dev,security,remote,market,fun. The script opened site/locales.mjs, found the two categories blocks with a regex, parsed English and Chinese names out of each, opened scripts/lib/entries.mjs, rewrote the CAT_IDS array to the same order, rewrote both category blocks in locales.mjs to match, and called node scripts/generate-readme.mjs. The output confirmed both files updated and printed the CAT_IDS list. Because I fed it the existing order, git diff showed no semantic change, which is exactly what you want from a reorder script invoked with a no-op order: it proves the round trip is stable and that the READMEs are generated from data, not hand edited. The README's claim that the list is curated and generated is backed by the code.

How it is built: the taxonomy is declared in two places that must agree, CAT_IDS in scripts/lib/entries.mjs and the two categories blocks in site/locales.mjs (one per locale, English and Chinese here). reorder-categories.py is the single tool that rewrites both and then regenerates the READMEs, which is the correct design since editing READMEs by hand would be undone on the next generate-readme.mjs run. entries.mjs also contains a validator that flags entries whose category is not in CAT_IDS and a function that maps over CAT_IDS to build sections, so the category list is the spine of both validation and rendering. locales.mjs is described in its own header as the single source of truth for internationalization, with instructions for adding a locale that touch README, banner, og image, and a privacy page body. The repo is large in file count, 1429 files across 6533 lines, which fits a data directory of per plugin YAML files plus generated docs rather than a lot of logic.

Quality from what I ran: the reorder script is careful. It asserts that the two locale blocks have matching keys and that the target list matches both, so a typo in the category order fails loudly before any file is written. It uses re.subn with count=1 and asserts n == 1, so it will not silently rewrite the wrong thing if CAT_IDS is missing or duplicated. It writes files back with utf-8 encoding. These are the marks of someone who has been burned by generated registries drifting. Rough edges: the license is unknown, which matters if you want to fork or republish the list. The test suite reportedly has an import failure, so CI may be green on generation but not on the Python test path. I only exercised the reorder path, not the site build, so I cannot speak to whether build-site.mjs runs clean.

Who should use it: anyone building or extending a DeepSeek Harness agent who wants to see what plugins already exist before writing one. It is also a usable template for anyone maintaining an awesome list that needs generated, multilingual READMEs with a real validation step. Where it bites: you must treat the READMEs as build artifacts, the taxonomy lives in two files and must stay in sync via the script, and the unknown license is a blocker for downstream reuse. For browsing plugins it is fine. For copying the tooling, check the license first.
