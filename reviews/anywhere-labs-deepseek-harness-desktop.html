I cloned anywhere-labs/deepseek-harness-desktop this week to see whether the 7000-star buzz is justified. The repo is a TypeScript desktop shell, 12501 lines across 174 files, MIT licensed, sitting on top of the DeepSeek Harness ecosystem. It is not a standalone application. It is an Electron bootstrap and plugin host that wraps the upstream deepseek-harness project, which lives in a git submodule under deepseek-harness/. The README is blunt about this: the file opens by saying it is a compatibility entry point and explicitly states it does not represent the upstream project. What Desktop actually owns is native window management, a tray, profile selection, a bundled terminal, and a pinned pnpm runtime. The upstream owns agent semantics. The boundary is deliberate and documented in the architecture notes.

Getting it running was straightforward in one sense and incomplete in another. The repository has no root package.json at the top level, which my run confirmed. The actual package manifests are nested under dsh-plugin-desktop/ and the submodule. I ran the documented setup script, which walked the tree, checked submodules, and printed source listings. The submodule was present. The test suite reported exit 127, which means the test runner command was not found or not wired up in the environment I used. The repo metadata claims 27 test files and CI is enabled, so the tests exist in the repository, but the documented usage did not invoke them successfully on my box. No additional system libraries were needed. The install did not require fixing missing dependencies. It ran on the first attempt for the bootstrap and inspection path.

The actual output I got was the architecture documentation, not a running window. The script printed the source tree, the AGENTS.md and README excerpts, and confirmed there is no binary entry point at the root. The most substantive output was the "why plugins" section from the architecture docs, which lays out the three reasons for the plugin model: upstream behavior stays replaceable, desktop behavior stays extensible, and ownership stays clear. It also lists what Desktop provides: native windows, tray, single-instance lifecycle on macOS and Windows, compatibility and advanced presentation modes, multiple profile selection, a bundled terminal, and public desktopProfiles and desktopPnpm Host services. The output confirms this is a host framework, not a user-facing app you launch and interact with directly.

Reading the source backs that up. dsh-plugin-desktop/src/main.ts is the Electron bootstrap: it imports app from electron, calls boot and installFailLoud from @deepseek-ai/dsh-app-boot, resolves the DSH home directory, installs a pnpm runtime, and then drives profile startup through beginDesktopProfileStartup and selectDesktopProfile from profile-manager.ts. The shutdown path goes through createDesktopExitCoordinator and createDesktopShutdown. dsh-plugin-desktop/src/index.ts is the Cordis host plugin, named desktop-shell, injecting desktopRuntime, webServer, webRuntime, appExit, and settings. It defines a Config schema with mode, width, height, minWidth, minHeight, defaulting to compatibility mode at 1280x840. The client side in src/client/index.ts is 26 lines and does almost nothing: it parses the environment from window.location.search and calls applyAdvancedShell only if mode is advanced. The heaviest file is desktop-terminal.ts at 753 lines, which builds an isolated terminal environment with platform-specific shims, Windows shell detection, executable file modes, and environment variable namespacing under DSH_DESKTOP_ prefixes.

The code is organized and the contracts are explicit. The inject arrays in index.ts and client/index.ts tell you exactly which services each layer depends on. The terminal module handles Windows quirks in detail: pwsh.exe, powershell.exe, cmd.exe, wt.exe, and a set of generated environment keys it cleans up. File permission constants like STATE_DIRECTORY_MODE at 0o700 and PRIVATE_FILE_MODE at 0o600 show attention to the right details. The schemastery schema validation for window config is strict, with min width 800 and min height 600 enforced at the schema level.

The rough edges I hit are real. The test suite did not run, reporting exit 127. The top-level README is a stub that redirects to docs/README.md, which is fine for navigation but means the entry point gives you nothing substantive. The project depends on a large number of @deepseek-ai/ scoped packages, so building the full thing requires the entire DSH monorepo context, not just this repo in isolation.

The verdict: this is for developers already invested in the DeepSeek Harness ecosystem who want a native desktop wrapper instead of a browser tab. It is not for someone looking for a standalone DeepSeek client. If you need the test suite, expect to debug the runner setup yourself. The architecture is sound, the plugin boundary is well reasoned, and the source is readable. Where it bites is the dependency surface and the test runner, which needs work before this is a smooth clone-and-build experience.

## Why plugins

Harness follows an “everything is a plugin” model. Desktop keeps the same principle for three practical reasons:

1. **Upstream behavior stays replaceable.** Desktop can use the official Web client, while a profile can add model, tool, UI, or workflow plugins.
2. **Desktop behavior stays extensible.** Profile management and the packaged package-manager environment can be exposed as explicit Host services instead of making every plugin guess at Electron internals.
3. **Ownership stays clear.** Upstream DSH owns agent semantics, Desktop owns native integration, and third-party plugins depend only on the contracts they need.

The plugin boundary also tells us what not to expose. Third-party plugins can use the public `desktopProfiles` and `desktopPnpm` services, but they cannot directly control `BrowserWindow`, the tray, Electron IPC, installers, or launcher-private paths. A stable contract is easier to upgrade and debug than an unrestricted private API.

## What Desktop provides

The current Desktop product provides:

- Native windows, a tray, and single-instance lifecycle on macOS and Windows.
- Compatibility and advanced presentation modes. Compatibility preserves the upstream client; advanced adds Desktop-owned layout, native materials, and drag regions.
- Multiple profile selection. Desktop exposes the active profile identity for the current generation, and switching takes effect through an orderly restart.
- A bundled terminal and pinned pnpm environment. They apply only to processes created by Desktop and do not modify the user's global PATH.
- Public `desktopProfiles` and `desktopPnpm` Host services for plugins.
- Version discovery and confirmation-gated installer downloads, handing off to a macOS DMG or Windows NSIS installer.

## What we deliberately do not do

- Reimplement the upstream Web UI as an Electron-native page.
- Override the upstream layout, sidebar, or conversation composition in compatibility mode.
- Copy records into a separate “Desktop database”; official profiles share the DSH home for sessions and settings by default.
- Give third-party plugins an undefined private Electron API.
- Present roadmap items such as a plugin marketplace, mobile remote control, or Channels as shipped features.
