TypeScript★ 3.2kMIT571,992 LOCran ✓ npm test exit 127

deepseek-harness-desktop is a TypeScript desktop client for the DeepSeek Harness (DSH) ecosystem, an agent and tool-calling framework centered on DeepSeek models. It presents itself as a modern desktop experience but the source reveals it is really the full agent runtime: a tool registry with execution pipelines, an event-sourced session store, a dynamic plugin host, and a UI slot system. The problem it solves is giving developers a local, controllable surface for running DeepSeek-powered agents that can call tools, run code, and manage multi-turn conversations with persistence, rather than relying on a hosted chat UI. It is MIT licensed and carries 3152 stars, with CI enabled and 709 test files across the monorepo.

The architecture is a Cordis-based plugin monorepo. The core tool system lives in `packages/core/tools/src/index.ts`, which is close to two thousand lines and implements a registry plus a pre/guard/around/post/result execution pipeline for tool calls. It depends on `@deepseek-ai/dsh-scope` for permission scoping via `ScopedLayers` and `scopeOf`, on `@deepseek-ai/dsh-llm` for content blocks and schema validation, and on `@deepseek-ai/dsh-agent` for the agent abstraction. A notable choice is that tool schemas are validated through `assertSupportedJsonSchema` and `validateJsonSchemaValue` before execution, and the package ships separate SDK renderers for TypeScript (`renderToolsSdk` in `ts-types.ts`) and Python (`renderToolsSdkPy` in `py-types.ts`), meaning the same tool registry can present its API to generated code in either language. The code mode in `code-mode.ts` defines `createRunCodeTool` with flavor-specific schema strings keyed by `CodeSdkLanguage`, and the registry explicitly fails if the loaded runtime language is not in its renderer table.

Session state is event-sourced in `packages/core/session/src/index.ts`. It keeps an append-only session log, an in-memory store, and a derived LLM message history. Persistence is deliberately deferred to plugins: the service emits `session/event` and expects a plugin to subscribe and drain on `session/flush`. `snapshotJsonValue` is used to freeze JSON values before they enter the log, and `SurfaceManager` in `surface.ts` handles the folding of replacement and append events into the message stream. The dynamic plugin host in `packages/extensions/cordis-host-runner/src/index.ts` is where things get more elaborate. It maintains immutable package definitions, allows one active run per plugin, requires human approval for client activation, and exposes host/client invocation through the `TypertRemoteService` protocol. Host-side code runs through `createSandbox`, `evaluateHostCode`, and `precheckCode` in `sandbox.ts`, with `isPlugin` and `normalizeHandler` guards in `guard.ts`.

On the client side, `packages/client/ui-slots/src/index.ts` is a zero-runtime-dependency slot registry. Owners declare slot contracts by merging into `SlotMap`, and a single `register` call can contribute a component plus child slots, a store seat, and a locale namespace. The `declare module` augmentation pattern is used so that consumers merge keys lexically into `SlotMap` and `LocaleNamespaceMap`, with the intersection types keeping the keys string-typed once merged.

We could not actually run the desktop app. The environment had Node and Python but no pnpm and no network access, and the repo is a pnpm monorepo. Our probe checked for entry points, found `apps/desktop/package.json`, `apps/cli/package.json`, and `python/sdk/pyproject.toml`, then attempted to import the Python SDK and reported "Importable modules with relevant names: NONE." The verdict from our run was "This is a pnpm-based desktop app. No pnpm/node available, no network. Cannot run pnpm install or pnpm run dev:desktop. No Python entry points declared. The repo is not runnable in this environment." The test suite returned exit 127, consistent with missing pnpm.

The code quality reads as serious and internally consistent. Types are strict, the scoping and validation seams are explicit, and the session layer is designed for replay rather than ad hoc state. The cordis host runner is the riskiest piece: it evaluates host code in a sandbox and gates client activation behind approval, but any dynamic plugin host is an attack surface, and the robustness of `evaluateHostCode` and `precheckCode` determines whether that boundary holds. The slot registry pattern is clever but depends on every consumer getting declaration merging right, which can produce confusing type errors when a merge is missing. The Python SDK at `python/sdk/pyproject.toml` depends on `deepseek-harness-runtime-bin==0.0.0.dev0`, a local companion package, which means the Python path is not standalone today. The 709 test files and CI are good signals, though we could not execute them.

Developers building DeepSeek agent workflows who want a local desktop surface and are willing to run a pnpm monorepo should look here. It is not a drop-in CLI or a pip installable Python package despite the SDK scaffolding, and anyone expecting the Python SDK to work without the runtime binary and a working Node toolchain will be disappointed. The dynamic plugin host is powerful but needs scrutiny before trusting it with untrusted plugins. Use it if you want the full DSH runtime on the desktop and can invest in the toolchain.
