I cloned anywhere-labs/deepseek-harness-desktop expecting a desktop shell and got something larger. The repo is a 571,992-line, 7,447-file TypeScript monorepo that implements "dsh", an agent harness from DeepSeek AI built on the Cordis plugin framework. The README's English heading "DeepSeek Harness" and the Chinese body describe an "everything is a plugin" architecture for composing agent tools, sessions, and surfaces. The desktop app is one entry point into that ecosystem, not the whole product. The core problem it targets is giving agent developers a typed, plugin-driven registry for tools, sessions, code execution, and UI slots, with a desktop and web surface on top.

Getting it running took three attempts. The first blocker was pnpm: the repo wants pnpm 11, which requires Node 22 or newer, but our box had Node 20. Installing pnpm 9.15.9 globally fixed that. With pnpm available, `pnpm install` pulled the dependency tree. The README gives two paths: `npx @deepseek-ai/dsh web` for the Web UI at 127.0.0.1:3080, or cloning and running `pnpm run build` then `pnpm dsh web`. We went for the desktop dev script. On a headless Debian box without a display, Electron cannot open a window, so we wrapped the run in `timeout 25` and set `ELECTRON_DISABLE_SECURITY_WARNINGS=1` to capture whatever Vite and the dev server printed before the display failure. The test suite reported exit 127, meaning the configured test command was not resolvable in our environment, so we could not run the 709 test files the metadata claims.

What we actually observed from `pnpm run dev:desktop` was not a running app but a dump of the root package.json scripts. The output lists dozens of verification scripts: `verify-config-source-ownership`, `verify-package-invariants`, `verify-built-package-invariants`, `verify-agent-note-classification`, `verify-type-equiv`, `verify-translation-pairing`, `verify-doc-budgets`, `verify-runtime-closure`, `verify-vendored-links`, and on. The same output shows `docs:dev`, `docs:build`, `website:dev`, and `website:build` delegating to a `@deepseek-ai/website` workspace package via `pnpm --filter`. This tells you two things. First, the repo is engineered around a large battery of custom invariants checks, not just unit tests. Second, the desktop dev path did not produce a visible result on our headless box, so we cannot confirm the UI renders. What we can confirm is that the build system is wired and the script surface is enormous.

The source backs that up. `packages/core/tools/src/index.ts` (1,947 lines) is the tool registry and execution pipeline, built on `@deepseek-ai/cordis` `Context` and `Service`, with `@deepseek-ai/schemastery` for schema validation. It imports scope types from `@deepseek-ai/dsh-scope`, LLM types from `@deepseek-ai/dsh-llm`, agent types from `@deepseek-ai/dsh-agent`, and session types from `@deepseek-ai/dsh-session`. The design is a pre, guard, around, post, result pipeline around tool calls, with JSON Schema validation via `assertSupportedJsonSchema` and `validateJsonSchemaValue`. A `CodeSdkLanguage` union and a renderer table map backend languages to SDK sections, and the comment notes that adding a language requires three parallel edits: a `CodeSdkLanguage` member, a table entry, and a `RUN_CODE_FLAVORS` entry in `code-mode.ts`. `packages/extensions/cordis-host-runner/src/index.ts` (1,275 lines) implements dynamic plugin loading with immutable package definitions, one active run per plugin, human-approved client activation, and host/client invocation over a `TypertRemoteService` remote protocol. `packages/core/session/src/index.ts` (1,158 lines) is an event-sourced session store: append-only log, in-memory state, derived LLM message history, with persistence left to plugins that subscribe to `session/event` and drain on `session/flush`. `packages/client/ui-slots/src/index.ts` (1,193 lines) is a slot registry for the UI layer, using TypeScript declaration merging on `SlotMap` and `LocaleNamespaceMap` so plugins declare typed component slots and locale namespaces with zero runtime dependencies beyond React types.

The quality signal from the code is strong. Comments are dense and explain why, not what. The `oxlint-disable` note in `ui-slots` explains that `keyof SlotMap & string` looks redundant in isolation but is the declaration-merge key pattern. The tool registry comment explains the `satisfies` clause pins the renderer table's key set to the `CodeSdkLanguage` union. This is code written by people who expect readers. The rough edges are operational. The pnpm 11 and Node 22 coupling is not documented in the README. The test suite did not resolve on our machine. The desktop path needs a display. CI is enabled and the MIT license is clean, but the 709 test files were not something we could execute.

I would use this if I were building a DeepSeek-based agent and wanted a typed, plugin-driven harness with session replay and a UI slot system. I would not use it if I needed a working desktop app today on a headless server or without Node 22. The honest takeaway is that the architecture is real and carefully built, the desktop surface is one consumer of it, and the install path has a versioning trap that will bite anyone who does not read the pnpm requirement first.

#!/usr/bin/env bash
set -euo pipefail

cd /tmp/rr/anywhere-labs_deepseek-harness-desktop

# pnpm 11 needs node>=22; install an older pnpm that works on node 20

pnpm --version
