I cloned anywhere-labs/deepseek-harness-desktop at version 2.0.2 to see what 19,261 stars actually buy you. The README opens with a Chinese-language redirect note pointing to README.md and docs/README.md, and explicitly says it does not replicate the upstream deepseek-harness project documentation. That is an honest signal: this repo is a desktop shell plugin built around a submodule called deepseek-harness, not a standalone product. The description calls it "a modern desktop experience built for the DeepSeek Harness ecosystem," which maps cleanly to what the code does. The core problem it addresses is giving the DeepSeek Harness command-line and webserver toolchain an Electron-native shell with profile management, a settings UI, a community plugin market, crash reporting, and directory picker dialogs that a pure web client cannot provide.

Getting it running took one attempt but required a system package. We ran apt-get install -y -qq xvfb because the primary entry point, dsh-plugin-desktop/src/main.ts, is a 1215-line Electron bootstrap that calls electron.app and opens a browser window. There is no CLI, no library export, no headless mode. Without a display server the app cannot start. The submodule at deepseek-harness was checked out at commit b150a551b8d465e31e418e1b2eaf5e79bbb7d28e, which we confirmed via git submodule status. The root package.json uses Yarn workspaces with three packages: dsh-community-fabric, dsh-plugin-desktop, and dsh-community-market. The build script chains yarn workspace dsh-community-market build followed by dsh-plugin-desktop build. The test script chains the workspace tests in the same order. So the install path is: init submodules, install system Electron dependencies including xvfb if you are headless, yarn install, then yarn build.

What actually happened when we ran it is the most telling part. We wrote a probe script that checked submodules, inspected all four package.json files, and attempted to launch under xvfb-run. The output confirmed the submodule was present and pinned. The root package.json has no bin and no main field, so there is no programmatic entry point. The scripts are build, typecheck, test, dev, start, dist:mac, dist:win, and packaging targets. We ran npm test and got exit code 1. The test suite is wired as yarn workspace dsh-plugin-desktop test followed by dsh-community-market test, plus architecture-gate checks like scripts/market-dependency-direction.test.mjs and a bilingual-docs verification script. The architecture gates enforce dependency direction so dsh-community-market cannot reach into dsh-plugin-desktop internals, and the bilingual-docs test ensures Chinese and English README files stay in sync. The failing tests mean something in the workspace test chain broke on our environment, which is a real rough edge for anyone cloning fresh.

The architecture is a Cordis plugin system. dsh-plugin-desktop/src/index.ts exports a Cordis plugin named desktop-shell that injects webServer and webRuntime services. The main.ts file bootstraps Electron, wires up crash reporting via crash-evidence.ts, uncaught exception logging via desktop-logger.ts, install recovery state via install-recovery.ts, and profile management through desktop-settings-route.ts. The client side in dsh-plugin-desktop/src/client/index.ts type-imports dsh-client-ui-renderer, dsh-client-ui-theme, and dsh-client-ui-settings, then applies advanced-shell, desktop-settings, a directory picker bridge, and a workspace folder drop handler. dsh-community-market is a separate plugin that registers market routes against a restricted HTTP client pinned to registry.npmjs.org, so community plugins install only from the official npm registry. The NPM registry verifier lives in install/service.js alongside MarketInstallService.

The codebase is 60,087 lines of TypeScript across 508 files with 93 test files and CI enabled. The license is MIT. The source is dense and intentionally layered: desktopBootRecoveryInjections, maskSecrets for log redaction, FileExporter and LogFileSink for diagnostics, createDesktopLifecycleRecorder for startup failure tracking. The type discipline is heavy, with schemastery validation and named contract constants like DESKTOP_DIRECTORY_PICKER_PATH and DESKTOP_PROFILE_CREATE_PATH separating route registration from handlers. The rough edges we hit: npm test fails on a clean clone, which undercuts the CI badge and means contributors will face a broken first run. The xvfb requirement is undocumented in the redirect README. The submodule dependency means a shallow clone will silently miss the upstream harness. The verdict: this is for developers already inside the DeepSeek Harness ecosystem who want a desktop shell around it, not for someone expecting a standalone DeepSeek client. Use it if you are extending DSH with Electron UI or community plugins, avoid it if you want a tool that tests green on first clone.
