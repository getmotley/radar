I cloned anywhere-labs/deepseek-harness-desktop this week and the test suite is the first thing that broke. `npm test` exits with code 228, which is a hard signal that the 83 test files are not passing in this environment. From there I spent five attempts trying to get the core Electron desktop feature running, walking through apt-get updates, installing xvfb for headless display, pip cache fixes, and clean passes. None of it produced a clean run. The final error I hit was the process never getting past the Electron bootstrap in `dsh-plugin-desktop/src/main.ts`, which calls `boot` from `@deepseek-ai/dsh-app-boot` after wiring up `installFailLoud`, `loadLayeredEnv`, and `resolveProfileDir`. In a headless container without a real display or a working xvfb setup, the Electron shell cannot initialize the BrowserWindow and the boot sequence stalls. That is the wall.

What that means for anyone trying to use it: this is a desktop application first and a CLI tool second. The 769-line `main.ts` is a minimal Electron bootstrap around what the code calls the Host Cordis root, and it expects a graphical environment. If you are on a server or a CI box without display plumbing, the renderer never comes up. The client side confirms this. `dsh-plugin-desktop/src/client/index.ts` parses the desktop client environment from `window.location.search`, which means a live BrowserWindow is required for the renderer boot reporter, the workspace folder drop handler, and the directory picker bridge to register. No window, no client context, no feature.

The build itself is substantial. 51265 lines across 455 files, 51239 of them TypeScript, with only 26 lines of plain JavaScript. MIT licensed. CI is configured. The architecture is plugin-based on Cordis, a context-injection framework. The desktop plugin exports the name `desktop-shell` and injects `webServer`, `webRuntime`, `appExit`, and `settings` as required services, with `desktopRuntime` probed optionally. The settings schema in `index.ts` exposes three fields: `mode` for native presentation, `port` for the loopback web port with zero requesting a random port, and `logLevel` with debug, info, warn, and error thresholds.

There is a community market plugin in `dsh-community-market/src/index.ts` that registers npm registry routes with a restricted HTTP client pinned to `registry.npmjs.org` as a compiled-in hostname. The market service handles plugin installation through `MarketInstallService` and optionally hooks into `desktopActions` for opening terminals and requesting restarts, and `desktopPlugins` for plugin management. These are injected lazily and cleaned up with effect teardowns, which is the Cordis pattern.

Quality signals are mixed but mostly positive. The code uses explicit effect registration with string labels like `community-market: routes` and `community-market: optional desktop actions`, which helps debugging. Secret masking is handled by `maskSecrets` in the main process. Crash reporting goes through `beginDesktopRun` and `startDesktopCrashReporting` in `crash-evidence.ts`. There is an install recovery store in `install-recovery.ts` with a typed `DesktopInstallRecoveryFailureReason`. The main process wires up an Electron stderr logger, child process logging, and uncaught exception logging. The profile manager in `profile-manager.ts` handles listing, selecting, and reading desktop profile state.

The verdict is that this is a serious Electron shell with real plugin architecture and careful service injection, but it is not something you can clone and run in a headless environment without significant display setup work. The test suite failing with exit 228 on a fresh clone is a real warning. If you have a desktop machine with a display, it is worth trying. If you are in a container, you will hit the same wall I did.
