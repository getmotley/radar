MengTo/threeui

TypeScript★ 4.7kMIT28,422 LOCran ✓ npm test exit 1

I cloned MengTo/threeui today to see what the 4,700 stars actually get you. The repo sells itself as an open-source, login-free edition of ThreeUI, a catalog of live interactive components built on Three.js and React. The specific problem it solves is giving frontend developers a library of high-production-value visual effects, things like temple night renderers, character carousels, and cloth simulations, without having to author the WebGL or shader code from scratch. It is essentially a component library where the catalog is the product, and the open-source version strips out the Pro and Beta components while keeping every free variant and its controls intact.

Getting it running took three attempts. The package ships with a set of scripts for typecheck, audit:public, test, build:site, and build:lib. The test script failed immediately with exit 1, which aligns with the metadata showing zero test files in the repo. There is no test suite to run. I had to work through the scripts individually to get a successful build. The sequence that finally worked was running npm run typecheck, then npm run audit:public, then npm run test, then npm run build:site, and finally npm run build:lib. Typecheck and the public boundary audit ran without blocking the process, though test just failed and moved on. The real success came from splitting the site build and the library build into separate steps. Running them in sequence produced the dist and lib-dist directories with the compiled assets.

The build output tells you exactly what this library is. Vite chunked the output into dozens of individual component files. The smaller ones like TypographyVortexCanvas came out to 9.82 kB and WarpFieldBackground to 11.04 kB. The larger ones reveal the actual weight of these effects. TextPathStudies is 85.32 kB, BrandOrbs is 163.05 kB, and NeuformBatchEffects is 347.11 kB. The biggest single chunk, BookshelfScene, is 1,538.01 kB, which gzips down to 793.81 kB. The three.module chunks alone account for over 900 kB combined. Vite emitted a warning about chunks larger than 500 kB. This confirms the library delivers on its promise of complex 3D components, but the cost is real. You are shipping megabytes of JavaScript for visual effects, and the build system does not pretend otherwise.

Looking at the source, the architecture is a generated entry point combined with isolated effect modules. The src/index.ts file is 106 lines of auto-generated exports from a script called generate-library-entry.mjs. It exports dozens of components like AmberHalftone, AnimatedTopDock, AudioWordmark, and ClothStudy. The actual implementation lives in src/shaders. The templeNightRenderer.js file is 2,537 lines of hand-tuned or generated Three.js code, complete with a canonical source SHA-256 hash in the header to verify it matches the original Kage temple experience. It uses a mulberry32 seeded random number generator and a classic 2D gradient noise function for its visuals. The NeuformIsolatedEffects.tsx file takes a different approach, importing 28 raw HTML source files as strings and presumably hosting them in iframes. There is also a buildSkillMarkdown.js script that generates AI agent skills with instructions to copy HTML byte-for-byte to preserve exact authored behavior.

The quality picture is mixed. The code is clearly engineered with care for visual fidelity, using frame-rate independent damping and prefers-reduced-motion checks in the renderer. But there are zero tests and the test script fails. CI exists according to the metadata but the local test experience is broken. The MIT license is permissive and clean. The roughest edge is the bundle size. If you import more than one or two of these components into a production app, you will ship megabytes of JavaScript. The BookshelfScene component alone is larger than some entire application bundles.

I would use this library for marketing pages, landing experiences, and portfolio sites where visual impact matters more than load time. I would not use it for a dashboard or a content-heavy app where performance and bandwidth are critical. The effects are real, the code is verbose, and the lack of tests means you are relying entirely on the author's visual fidelity checks rather than automated regression protection. It does what it claims, but you pay for it in bytes.

What it took: 3 attempts to get running; we installed/fixed: npm run build..., npm run build 2, npm package name from package.json:, npm run test 2, npm run audit:public 2.

#!/usr/bin/env bash
set -euo pipefail
cd /tmp/rr/MengTo_threeui

echo "=== Inspect package.json scripts ==="
cat package.json | python3 -c "import sys,json; d=json.load(sys.stdin); [print(f'  {k}: {v}') for k,v in d.get('scripts',{}).items()]" 2>/dev/null || grep -A30 '"scripts"' package.json

echo ""
echo "=== Step 1: Typecheck ==="

  echo "typecheck: OK"
else
  echo "typecheck: failed (continuing)"
fi

  echo "audit:public: OK"
else
  echo "audit:public: not available or failed"
