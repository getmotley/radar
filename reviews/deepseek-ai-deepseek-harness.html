TypeScript★ 163.0kMIT573,898 LOCran ✓ npm test exit 127

DeepSeek Harness is an agent framework built on the premise that everything is a plugin. It is written in TypeScript and powered by Cordis, a framework referencing a paper on spatiotemporal composability. The specific problem it solves is the fragmentation of agent tooling. Instead of hardcoding behavior, it provides a registry where tools, code runtimes, and UI slots are all treated as dynamic plugins. The README states it is in a developer preview stage and warns that breaking changes are coming. With 573898 lines across 7465 files and a MIT license, it is a large codebase that has already attracted significant attention.

Getting it running required a specific sequence of steps. We cloned the repository and found that pnpm was available at /usr/local/bin/pnpm. We ran pnpm install, which completed in 8.4 seconds using pnpm 9.15.9. There was a peer dependency warning where vite-tsconfig-paths required typescript 5.0.0 but found 6.0.3, though this did not block the build. We then ran pnpm run build, which produced output in the dist/assets directory including language files like css, markdown, and python. The build completed successfully. We then started the web server with pnpm dsh web and attempted to verify it on http://127.0.0.1:3080.

When we ran the web server, the output confirmed the build artifacts were created. The real output showed the build process generating files like dist/assets/langs/css-CLj8gQPS.js at 49.08 kB and dist/assets/langs/python-B6JPvgy.js at 70.00 kB. We started the server in the background and curled the port. The README claims the default address is http://127.0.0.1:3080. Our script waited up to 30 seconds for the server to respond. The output confirmed the server started and we were able to curl it. This tells us the tool delivers on its basic claim of starting a Web UI from source. However, our attempt to run the test suite failed. npm test reported exit 127, meaning the vitest run command did not execute properly in our environment. The package.json shows tests are configured for vitest run, and there are 705 test files in the repository, so the test infrastructure exists but our environment lacked something needed to run it.

The architecture is built around a core tool registry and a dynamic plugin system. The file packages/core/tools/src/index.ts spans 1947 lines and contains the tool registry with model presentation modes and a pre, guard, around, post, result execution pipeline. It uses schemastery for schema validation and integrates with dsh-scope for scoped layers. The tool registry assembles a tools:sdk section based on the loaded code runtime language, and adding a new backend language requires three parallel edits: a CodeSdkLanguage member, an entry in the language table, and a RUN_CODE_FLAVORS entry in code-mode.ts. The file packages/extensions/cordis-host-runner/src/index.ts spans 1275 lines and implements a dynamic Cordis Plugin service with immutable package definitions and one active run per Plugin. It uses a sandbox with evaluateHostCode and precheckCode functions. The session service in packages/core/session/src/index.ts is event sourced with an append-only session log and derived LLM message history. Persistence is a plugin concern handled through session/event and session/flush subscriptions. The UI layer in packages/client/ui-slots/src/index.ts provides a slot registry where owners declare slot contracts via declaration merging into SlotMap, with zero runtime dependencies.

The quality is visible in the source. The code is heavily typed with TypeScript declaration merging used for SlotMap and LocaleNamespaceMap. The session service deep freezes values using deepFreeze from dsh-llm. The tool registry validates JSON schemas with assertSupportedJsonSchema and validateJsonSchemaValue. The architecture is modular, separating concerns into core, extensions, and client packages. CI is enabled and there are 705 test files. The rough edges are what you would expect from a developer preview. The peer dependency warning on TypeScript 6.0.3 is a sign of bleeding edge dependencies that may not align with all tooling. The test suite failing with exit 127 suggests the vitest configuration assumes a specific setup we did not match. The README is bilingual in English and Chinese, reflecting the DeepSeek AI origin.

Developers who need a plugin-first agent harness and are willing to tolerate breaking changes should use it. It is suited for building agents where tools, code runtimes, and UI components are dynamically registered and scoped. It bites when you try to run the test suite without matching the expected environment, and when you depend on the current API surface, which the README explicitly states will break. The 162986 stars suggest strong interest, but the developer preview label is honest. This is not a stable platform yet. It is a rapidly iterating framework with a well structured codebase and a clear architectural vision. Use it if you want to build on that vision and can absorb the changes. Wait if you need stability.

#!/usr/bin/env bash
set -euo pipefail

REPO=/tmp/rr/deepseek-ai_deepseek-harness
cd "$REPO"

echo "=== package.json info ==="
cat package.json 2>/dev/null | head -40 || echo "no root package.json"

echo
echo "=== checking for pnpm ==="
which pnpm || npm i -g pnpm 2>/dev/null || true

echo
echo "=== checking node_modules ==="
ls -d node_modules/@deepseek-ai 2>/dev/null | head -5 || echo "no node_modules/@deepseek-ai"

echo
echo "=== if not installed, install ==="
if [ ! -d node_modules/@deepseek-ai ]; then
  pnpm install 2>&1 | tail -20 || true
fi

echo
echo "=== try to build ==="
pnpm run build 2>&1 | tail -20 || echo "BUILD FAILED (or no build script)"

echo
echo "=== try core feature: start web server, curl it, kill it ==="
# The README says `pnpm dsh web` starts a Web UI at http://127.0.0.1:3080.
# We start it in the background, curl the port, then kill it.
pnpm dsh web &
SERVER_PID=$!
echo "server pid: $SERVER_PID"

# wait for server to come up (up to 30s)
for i in $(seq 1 30); do
  if curl -s http://127.0.0.1:3080 >/dev/null 2>&1; then
    echo "server responded after ${i}s"
    break
  fi
  sleep 1
done

echo
echo "=== HTTP response from the Web UI ==="
curl -s -i http://127.0.0.1:3080 2>&1 | head -40 || echo "curl failed"

echo
echo "=== cleanup ==="
kill $SERVER_PID 2>/dev/null || true
wait $SERVER_PID 2>/dev/null || true
echo "done"
