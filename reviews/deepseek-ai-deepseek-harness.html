DeepSeek Harness, the `dsh` CLI, is an open source agent framework from DeepSeek AI built on the principle that "everything is a plugin." It is driven by Cordis, a framework referencing a paper on spatiotemporal composability. At 616,539 lines across 7,890 files, it is a massive TypeScript monorepo, currently in a developer preview stage with the explicit warning that breaking changes are coming. The problem it targets is agent infrastructure fragmentation: it provides a single harness where tools, sessions, code runtimes, and UI slots are all pluggable extensions rather than hardcoded subsystems. The promise is that you can wire up a web UI, register tools dynamically, and get an agent running without rebuilding the core.

Getting it running took three attempts. The README says to run `pnpm install`, `pnpm run build`, and `pnpm dsh web`. We cloned the repo to `/tmp/rr/deepseek-ai_deepseek-harness` and hit the first wall immediately: pnpm tried to use a store at `/.pnpm-store` and ran out of disk space. The fix was exporting `PNPM_HOME=/tmp/pnpm-home` and `PNPM_STORE_DIR=/tmp/pnpm-store` to relocate the package cache. Even then, downloads failed repeatedly. The log shows `ERR_PNPM_ENOSPC` errors across core dependencies: vite, sharp, zod, ws, the Agent Client Protocol SDK, and react-dom all failed to fetch with the message "Will retry in 10 seconds." We fell back to `pnpm install --ignore-scripts` to skip native build steps. We also saw platform mismatch warnings for `native/landlock-run/packages/linux-arm64` on our x64 machine, plus cyclic workspace dependency warnings between packages like `packages/api/gateway` and `packages/client/connection`. We ran `pnpm run build || true` because the build was unreliable given the incomplete install.

When we finally ran `pnpm dsh web --no-open`, the server did not deliver a working UI. The output is dominated by pnpm install warnings, not server startup logs. There is no "listening on 127.0.0.1:3080" line, no URL, no ready message. The tool claims to start a Web UI at port 3080 and open a browser on local launches, but we observed neither. The ENOSPC errors during dependency fetch meant the install was incomplete, so the build had missing workspace packages and the web command could not boot. This tells you the real barrier is not the code logic but the install footprint: the monorepo pulls hundreds of packages, needs disk space for a large pnpm store, and fails ungracefully when space is tight.

The architecture is visible in the source. `packages/core/tools/src/index.ts` is a 1,947-line tool registry implementing a pre, guard, around, post, and result execution pipeline with JSON Schema validation via `assertSupportedJsonSchema` and `validateJsonSchemaValue`. It supports multiple code SDK languages through `CodeSdkLanguage` and `renderToolsSdkPy`, with `createRunCodeTool` building the `run_code` tool. `packages/extensions/cordis-host-runner/src/index.ts` provides dynamic plugin loading with `DynamicCordisRegistry`, sandboxed code evaluation through `createSandbox` and `evaluateHostCode`, and human-approved Client activation. `packages/core/session/src/index.ts` is an event-sourced session service with an append-only log and `SurfaceManager` for derived LLM message history. `packages/client/ui-slots/src/index.ts` handles UI composition through declaration merging on `SlotMap` and `LocaleNamespaceMap`, letting plugins register React components into typed slots. The design is consistent: services extend Cordis context interfaces, scope is managed through `@deepseek-ai/dsh-scope`, and persistence is a plugin concern subscribing to `session/event`.

The code is dense and heavily typed, clearly not a weekend project. The test suite has 753 files and CI is enabled. The license is MIT. But the rough edges are real. The cyclic workspace dependency warnings across multiple package groups suggest the monorepo topology needs cleanup. The native landlock package ships platform-specific binaries that warn on mismatched architectures. Our own `npm test` run exited with code 127, meaning the test command could not execute in our environment. The install is the fragile part: it requires substantial disk space for the pnpm store and native dependencies that may not build cleanly across platforms.

If you want to study a plugin-first agent harness architecture, the source is worth reading for its tool pipeline, session event sourcing, and slot-based UI composition. If you want to run it today, allocate disk space, set `PNPM_STORE_DIR` to a partition with room, and expect to troubleshoot native dependencies. The developer preview label is accurate. This is not production-ready tooling. It is a research-grade framework with interesting ideas about plugin composability that currently bites on the install before you reach the features.

What we ran

We installed and ran it ourselves. Here is what it took, the exact command, and the real output from our box. Nothing edited.

What it took: 3 attempts to get running; we installed/fixed: npm on PATH per the environment, npm install, npm run build, npm dsh web, npm dsh web --no-open.

#!/usr/bin/env bash
set -euo pipefail

cd /tmp/rr/deepseek-ai_deepseek-harness

# Previous run hit ENOSPC at /.pnpm-store. Redirect the store to /tmp which has space.
export PNPM_HOME=/tmp/pnpm-home
export PNPM_STORE_DIR=/tmp/pnpm-store
mkdir -p "$PNPM_STORE_DIR"

# Retry install with the relocated store; fall back to --ignore-scripts if native deps fail.
pnpm install || pnpm install --ignore-scripts || true

# Build may fail if some workspace packages are broken; try anyway.
pnpm run build || true

LOG=/tmp/dsh_web.log
PORT_LOG=/tmp/dsh_port.log
: > "$LOG"

# Start the web server headless. --no-open prevents spawning a browser on a headless box.
timeout 25 pnpm dsh web --no-open >"$LOG" 2>&1 &
SERVER_PID=$!

# Poll up to ~20s for a listening line.
for i in $(seq 1 200); do
  if grep -qiE '127\.0\.0\.1:3080|localhost:3080|listening|ready|started|server|url|http' "$LOG" 2>/dev/null; then
    break
  fi
  if ! kill -0 "$SERVER_PID" 2>/dev/null; then
    break
  fi
  sleep 0.1
done

echo "===== dsh web output ====="
cat "$LOG"
echo "===== end ====="

# If the server is alive, try to curl the port it mentioned (default 3080).
if kill -0 "$SERVER_PID" 2>/dev/null; then
  PORT=$(grep -oE ':[0-9]{4}' "$LOG" | head -1 | tr -d ':' || true)
  PORT=${PORT:-3080}
  sleep 1
  echo "===== curl 127.0.0.1:$PORT ====="
  curl -sS --max-time 5 "http://127.0.0.1:$PORT/" 2>&1 | head -50 || true
  echo "===== end curl ====="
  kill "$SERVER_PID" 2>/dev/null || true
  wait "$SERVER_PID" 2>/dev/null || true
else
  echo "Server process exited early; see log above."
  # Show exit code
  wait "$SERVER_PID" 2>/dev/null && echo "exit: $?" || echo "exit: non-zero / killed"
fi
