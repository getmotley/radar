DeepSeek Harness is an open source agent framework from DeepSeek AI, built around a single architectural idea: everything is a plugin. The codebase is large, 622,317 lines across 7,902 files, with TypeScript as the primary language and smaller amounts of Python and Shell. It uses Cordis, a plugin framework tied to a research paper on spatiotemporal composability. The problem it targets is the construction of LLM agents that can dynamically load, inspect, and execute tools without hardcoding the available capabilities into the agent loop. The framework provides a registry for tools, a session service for event-sourced message history, and a host runner for dynamic plugin activation with human approval gates.

Getting it running required a specific sequence of steps. The README says to run `npx @deepseek-ai/dsh web` or build from source with pnpm. We cloned the repository and followed the source path. We first had to ensure pnpm was installed globally via `npm install -g pnpm`. We ran `pnpm install`, which completed in 9.4 seconds using pnpm v9.15.9 but produced a peer dependency warning: `vite-tsconfig-paths` requires `typescript@^5.0.0` but found `typescript@6.0.3`. This warning did not block the build. We then ran `pnpm run build`, which completed in 3.20 seconds and produced a Vite-based web UI bundle in the `dist` directory. The build did emit a chunk size warning for files larger than 500 kB after minification, including a 744.87 kB vendor bundle and a 637.59 kB C++ language grammar bundle, but this is advisory only. The command that finally worked was `pnpm dsh web --no-open`, which we ran with a 10 second timeout to start the server and test it.

When we started the web UI server, it listened on `http://127.0.0.1:3080`. We hit that address with curl and confirmed the server responded. The output from the build phase shows the toolchain successfully compiled the web client assets, including language grammar files for Python, C, C++, Ruby, and others, plus a main `index` chunk of 399.36 kB and the large vendor chunk. The build recorded 200 client artifacts. The server started without error. This tells us the framework does deliver a working local web interface as described in the README, though the README states the project is in a developer preview stage with breaking changes expected.

The architecture is visible in the source. The tool registry in `packages/core/tools/src/index.ts` implements a pipeline with pre, guard, around, post, and result execution phases. It imports `Context` and `Service` from `@deepseek-ai/cordis` and uses a schema validation library called `schemastery`. The registry manages tool presentation modes and assembles SDK sections for different code runtime languages, with a table that maps each language to a renderer function. The file `packages/extensions/cordis-host-runner/src/index.ts` handles dynamic plugin execution. It defines immutable package definitions, allows one active run per plugin, and requires human-approved client activation. It imports a `CordisInspectRegistryService` and a `DynamicCordisRegistry` to manage plugin inspection and invocation. The session service in `packages/core/session/src/index.ts` is event-sourced: it maintains an append-only session log and an in-memory store, deriving LLM message history from events. Persistence is handled as a plugin concern via subscription to `session/event` and `session/flush`. The UI layer in `packages/client/ui-slots/src/index.ts` uses a declaration merging pattern for slot contracts, where owners extend a `SlotMap` interface and a `LocaleNamespaceMap` interface to register components and locale dictionaries.

The quality picture is mixed but real. The project has 760 test files and CI configured. The license is MIT. The codebase is substantial and the module boundaries are clear, with separate packages for core tools, session management, code runtime, and client UI. The peer dependency mismatch with TypeScript 6.0.3 is a rough edge: it did not break the build but signals the dependency pins are not yet updated for the current TypeScript release. The chunk size warnings in the web build indicate the client bundle is not code-split, which could affect load times in a browser. We could not run the test suite ourselves: `npm test` exited with code 127, meaning the test command was not found or not properly configured in our environment. The framework is usable for developers who want to build agent systems with a plugin-based architecture and are willing to tolerate the developer preview instability. It bites where the dependency chain is fragile, the test runner setup is unclear, and the web bundle is monolithic.

#!/usr/bin/env bash
