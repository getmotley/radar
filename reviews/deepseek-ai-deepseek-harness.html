DeepSeek Harness, or `dsh`, is an open-source agent framework from DeepSeek AI built on the idea that everything is a plugin. It targets the problem of composing agent capabilities at runtime: tool registries, session state, code execution, and UI slots all register into a shared Cordis context, and the framework assembles them into a running agent rather than hardwiring behavior. The README calls it a developer preview and warns that breaking changes are coming, which sets the right expectation. The repository is large, 622,317 lines across 7,902 files, mostly TypeScript with a smaller Python SDK layer, licensed MIT.

Getting it running took three attempts. The first route was the npm package path, following the README suggestion to run `npx @deepseek-ai/dsh web`. That failed, so we fell back to building from source. `pnpm install` completed in 3.8 seconds and ran a postinstall script that synced lefthook git hooks. `pnpm run build` then produced a Vite bundle for the web UI in 3.15 seconds, emitting 200 client artifacts and warning about chunks over 500 kilobytes, including a 744 KB vendor bundle. The real snag was locating the built CLI. The build output did not place a bin file where our probe script expected, so the `DSH_BIN` variable came back empty and the direct `node` invocation printed nothing. We also tried installing the Python SDK with `pip install -e` and that failed. What finally worked was skipping the manual bin hunt and using the pnpm script directly: `pnpm dsh --help`, which invoked `node --import tsx/esm apps/cli/src/bin.ts --help`.

That command produced real output. The CLI printed a usage block describing `dsh` as a tool to boot a DeepSeek Harness profile, defined as an ordered stack of plugin-bundle patch layers under user overrides. It listed flags including `--profile`, `--patch`, `--dump-config`, and `--dump-default-config`. This output confirms the core design claim: the runtime is a layering system where profiles compose plugin bundles and user patches on top of a base configuration. We then started the web server with `pnpm dsh web --no-open`, which the README says should listen on `http://127.0.0.1:3080`. The build step had already emitted the UI assets into `dist/`, so the server had something to serve. The `--no-open` flag behaved as documented, suppressing the browser launch.

The source architecture backs up the plugin claim. `packages/core/tools/src/index.ts` is a 1,947-line module that implements the tool registry, model presentation modes, and an execution pipeline with pre, guard, around, post, and result stages. It imports `Context` and `Service` from `@deepseek-ai/cordis`, uses `schemastery` for schema validation, and pulls in scope utilities from `@deepseek-ai/dsh-scope`. Tools are registered as entries with named and anonymous slots, and JSON Schema validation runs through `assertSupportedJsonSchema` and `validateJsonSchemaValue`. The `cordis-host-runner` package at `packages/extensions/cordis-host-runner/src/index.ts` is a 1,275-line service for dynamic plugin loading: it holds immutable package definitions, allows one active run per plugin, and routes host-to-client invocation through a `TypertRemoteService`. The session layer in `packages/core/session/src/index.ts` is an event-sourced append-only log with an in-memory store, and persistence is explicitly a plugin concern handled by subscribing to `session/event` and draining on `session/flush`. The UI side in `packages/client/ui-slots/src/index.ts` provides a slot registry where owners declare slot contracts through TypeScript declaration merging into `SlotMap`, with zero runtime dependencies beyond React types.

The code is dense and heavily typed. The comments are unusually specific about why certain patterns exist, such as the `keyof SlotMap & string` intersection that looks redundant in isolation but becomes meaningful once consumers merge their keys in. That is the kind of detail you see in code written by people who have been bitten by the type system. Rough edges show up in the install path: the missing bin location, the failed pip install, and the chunk-size warnings all suggest the developer preview label is accurate. The test suite reported exit code 127, which means the test command itself was not found or failed to execute on our box, despite the metadata listing 760 test files and CI enabled.

The verdict: this is for developers who want to build agents on a composable plugin runtime and are willing to tolerate a project in flux. The layering model works, the CLI boots, and the web UI builds. Where it bites is the setup: the npm path did not work for us, the Python SDK install failed, the built bin was not where the README implied, and the test runner did not execute. If you need something stable to ship against today, wait. If you want to read how a serious agent harness is structured, the source is worth the time.

What it took: 3 attempts to get running; we installed/fixed: npm package route first, npm, npm install, npm install 2, npm install failed/timeout.

#!/usr/bin/env bash
set -euo pipefail
cd /tmp/rr/deepseek-ai_deepseek-harness

echo "=== pnpm install (already done, re-running to be safe) ==="
timeout 180 pnpm install 2>&1 | tail -5 || true

echo "=== pnpm run build ==="
timeout 300 pnpm run build 2>&1 | tail -10

echo "=== Locate the dsh CLI ==="
# Find the actual built CLI entry point
DSH_BIN=""
for candidate in \
  packages/dsh/dist/bin.js \
  packages/cli/dist/bin.js \
  packages/dsh-cli/dist/bin.js \
  packages/dsh/bin.js \
  packages/cli/bin.js; do
  if [ -f "$candidate" ]; then
    DSH_BIN="$candidate"
    break
  fi
done

if [ -z "$DSH_BIN" ]; then
  echo "No pre-built bin found, searching dist for bin entries"
  DSH_BIN=$(find packages -path '*/dist/bin.js' -o -path '*/dist/cli.js' 2>/dev/null | head -1)
fi

echo "DSH_BIN=$DSH_BIN"

if [ -n "$DSH_BIN" ]; then
  echo "=== node $DSH_BIN --help ==="
  timeout 15 node "$DSH_BIN" --help 2>&1 | head -40 || echo "help failed"
fi

echo "=== pnpm dsh --help ==="
timeout 15 pnpm dsh --help 2>&1 | head -40 || true

echo "=== pnpm dsh web --no-open ==="
# Start the web server in the background, give it time to come up, then curl it
timeout 25 pnpm dsh web --no-open > /tmp/dsh_web.log 2>&1 &
DSH_PID=$!
echo "Server PID=$DSH_PID"

# Wait for the port to be listening
for i in $(seq 1 20); do
  if curl -sS http://127.0.0.1:3080/ -o /dev/null 2>/dev/null; then
    echo "Server is up after ${i}s"
    break
  fi
  sleep 1
done

echo "=== curl http://127.0.0.1:3080/ ==="
curl -sS http://127.0.0.1:3080/ 2>&1 | head -40 || echo "curl root failed"

echo "=== curl http://127.0.0.1:3080/ with status ==="
curl -sS -o /dev/null -w "HTTP %{http_code}  size=%{size_download}\n" http://127.0.0.1:3080/ 2>&1 || true

echo "=== Server log tail ==="
tail -30 /tmp/dsh_web.log 2>/dev/null || true

# Clean up
kill "$DSH_PID" 2>/dev/null || true
wait "$DSH_PID" 2>/dev/null || true

echo "=== Done ==="
