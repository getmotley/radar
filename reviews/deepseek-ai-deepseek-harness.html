DeepSeek Harness, or `dsh`, is an open source agent framework from DeepSeek AI built on a single architectural idea: everything is a plugin. It runs on top of Cordis, a composition framework tied to a research paper on spatiotemporal composability. The repo is large by any measure, 569,789 lines across 7,411 files, with TypeScript dominating at 564,281 lines and smaller amounts of Python, Shell, and JavaScript. It is MIT licensed, has CI enabled, and ships roughly 700 test files. The README pitches a Web UI you can launch with `npx @deepseek-ai/dsh web`, but warns you up front that this is a developer preview and breaking changes are coming. The problem it tries to solve is the same one every agent harness tackles: how to give an LLM a consistent tool interface, a session memory, and an extension model that does not collapse as you add capabilities. The answer here is a plugin-first design where tools, sessions, code runtimes, and UI slots are all wired through a shared registry and scope system.

Getting it running was not a clean one-liner. The repo uses a pnpm workspace with a deliberately complex layout: vendored framework packages under `vendor/*`, core packages under `packages/*/*`, native Landlock launcher code under `native/landlock-run`, product assemblies under `apps/*`, a website, examples, and a Python SDK runtime. The `pnpm-workspace.yaml` pins overrides so `@deepseek-ai/cosmokit` and `@deepseek-ai/schemastery` resolve to local vendored sources rather than published versions. It also uses pnpm 10 strict build allowlists, only permitting `esbuild` and `lefthook` to run install scripts. I had Node 20.19.2 available with `npx` but no `pnpm` on PATH initially. The test suite never actually ran: `npm test` exited 127, meaning the test runner was not found or not wired at the root level. I had to install pnpm, then run `pnpm install`, which pulled the workspace together, then `pnpm run build` to compile the TypeScript packages. After that the `dsh` CLI binary should appear under `node_modules/.bin/` or in `packages/cli/dist/`. The build step is not optional: the source is TypeScript and the CLI entrypoints expect compiled output.

When I tried to start the Web UI with an 8-second timeout to capture boot output, the session ended without a clear log line or a confirmed listening port. The run produced the workspace and install diagnostics but no evidence that `dsh web` actually bound to `http://127.0.0.1:3080` as the README claims. This could be a missing environment variable for an API key, a build artifact that did not land where the CLI expected, or a runtime error that the timeout swallowed. The honest takeaway: the one-command `npx` path is the intended entrypoint, but from a fresh clone you are in for a multi-step build, and the Web UI did not demonstrably start in my run.

The source reads like a serious framework, not a weekend hack. The tool registry in `packages/core/tools/src/index.ts` (1,947 lines) is the heart of the system. It defines a tool pipeline with pre, guard, around, post, and result stages, backed by JSON Schema validation via `assertSupportedJsonSchema` and `validateJsonSchemaValue`. Tools are registered against a scope system (`AnonymousEntries`, `NamedEntries`, `ScopedLayers`, `scopeOf`, `scopeTarget`) that controls visibility and access. The file wires in `CodeRuntime` for language-specific SDK rendering, with a `CodeSdkLanguage` union and parallel tables for rendering TypeScript and Python tool type definitions. The `renderToolsSdk` and `renderToolsSdkPy` functions generate language-appropriate SDK sections for the model. The session service in `packages/core/session/src/index.ts` (1,158 lines) is event-sourced: an append-only log with an in-memory store and derived LLM message history. Persistence is explicitly a plugin concern, handled by subscribing to `session/event` and draining on `session/flush`. The `SurfaceManager` and `deriveEventMessage` functions translate raw events into the message stream the LLM consumes. The Cordis host runner in `packages/extensions/cordis-host-runner/src/index.ts` (1,275 lines) manages dynamic plugin execution: immutable package definitions, one active run per plugin, human-approved client activation, and a sandbox via `createSandbox`, `evaluateHostCode`, and `precheckCode`. The UI slot system in `packages/client/ui-slots/src/index.ts` uses TypeScript declaration merging to let owners declare slot contracts and locale namespaces with zero runtime dependencies beyond React types.

The code quality is high in the parts I read. Type safety is enforced through declaration merging patterns for `SlotMap` and `LocaleNamespaceMap`, and the `satisfies` clause on the SDK renderer table pins the key set to the `CodeSdkLanguage` union so adding a backend language requires three parallel edits. The 700 test files and CI configuration suggest real coverage, though I could not run the suite myself. The rough edges are practical: the build is multi-step, the test runner was not invocable from the root, and the Web UI did not start cleanly in my environment. This is a framework for developers building agent systems who want fine-grained control over tool pipelines, session semantics, and plugin isolation. It is not a drop-in chatbot. If you need something that runs in 30 seconds, look elsewhere. If you want to understand and extend an agent harness with a principled scope and plugin model, the source rewards reading. The breaking-changes warning in the README should be taken literally: pin your version if you build on this.

#!/usr/bin/env bash
set -euo pipefail

cd /tmp/rr/deepseek-ai_deepseek-harness

# We have a venv and node_modules. Check what's actually installed.
echo "=== Node/pnpm state ==="
which node pnpm npx 2>/dev/null || true
node --version 2>/dev/null || true
ls node_modules/.bin/ 2>/dev/null | head -20 || true

echo
echo "=== pnpm workspace ==="
cat pnpm-workspace.yaml 2>/dev/null || echo "(no pnpm-workspace.yaml)"
cat package.json 2>/dev/null | head -40 || echo "(no root package.json)"

echo
echo "=== Python SDK state ==="
.rrvenv/bin/python --version 2>/dev/null || true
.rrvenv/bin/pip list 2>/dev/null | head -20 || true

echo
echo "=== packages present ==="
ls packages/ 2>/dev/null || echo "(no packages dir)"

echo
echo "=== Try pnpm install ==="
pnpm install 2>&1 | tail -30 || echo "pnpm install failed"

echo
echo "=== Try pnpm run build ==="
pnpm run build 2>&1 | tail -40 || echo "pnpm build failed"

echo
echo "=== Check if dsh binary exists ==="
ls -la node_modules/.bin/dsh 2>/dev/null || echo "no dsh binary"
ls -la packages/cli/dist/ 2>/dev/null || echo "no cli dist"
find . -name "dsh" -type f 2>/dev/null | head -5 || true

echo
echo "=== Try starting the web UI on a port, capture startup output ==="
# Give it 8 seconds to boot then kill it; print whatever it logged.
timeout 8 pnpm dsh web 2>&1 || true

echo
echo "=== If that failed, try the Python SDK import path ==="
.rrvenv/bin/python -c "
import sys
sys.path.insert(0, 'python/sdk')
sys.path.insert(0, 'python/sdk-runtime')
try:
    import deepseek_harness
    print('imported deepseek_harness:', deepseek_harness)
except Exception as e:
    print('import failed:', e)
try:
    import dsh
    print('imported dsh:', dsh)
except Exception as e:
    print('dsh import failed:', e)
" 2>&1 || true

echo
echo "=== Last resort: curl the default port in case it did start ==="
curl -sS http://127.0.0.1:3080/ 2>&1 | head -20 || true
