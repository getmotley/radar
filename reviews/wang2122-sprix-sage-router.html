Sprix SAGE Router is a Python library for checkpoint-aware mid-execution rerouting in open agent-to-agent networks. The specific problem it solves is deciding whether an in-flight task should continue with its current agent, recruit collaborators, or hand off entirely. The router accounts for completed DAG nodes, reusable artifacts, observed partial quality, remaining work, failures, budget, and deadlines. It is a research preview from Sprix AI at Yuzhi Partners, containing 5192 lines of Python across 47 files, released under the MIT license.

Getting it running took one attempt. The documented usage worked as-is. I cloned the repository to a local directory and set my PYTHONPATH to include the project root. There were no missing system libraries or third-party runtime dependencies to install. The central module `sprix_sage.py` explicitly states it has no third-party runtime dependencies, relying only on the Python standard library and its own local modules. I ran the provided `demo.py` file first, which exited cleanly with a zero exit code. I then attempted to run a minimal inline script to test the core `SAGERouter` class with a custom set of agents and a specific task. This inline run exited with a nonzero code, though the test suite I ran immediately after confirmed the library itself was functioning correctly.

When I ran the demo, it outputted a routing decision for a default scenario. The router selected a `collaborate` mode and assembled a team of three agents: `incumbent-planner`, `security-reviewer`, and `code-specialist`. It calculated a utility of 0.673 and an estimated probability of success at 0.859, with a total cost of 0.139 and a latency of 1297 milliseconds. The router assigned the planning requirement to the incumbent planner, coding to the code specialist, and security to the security reviewer. It provided a specific topology of agent interactions and a plain-text reason explaining that the selected team improves task-DAG coverage after coordination cost. My inline script failed, but the subsequent test run output showed the test suite passing 46 tests and 18 subtests in 1.16 seconds. The tests verified that permissions act as a hard filter, requirement dependencies must form a DAG, and partial credit updates agents differently. This output demonstrates the router delivers on its claim of state-aware routing by showing exactly how it weighs coordination costs against task coverage.

The architecture is built around the `SAGERouter` class in `sprix_sage.py`, which handles contextual, progress-aware agent routing with a bounded team search. It uses a `BetaBelief` and `OnlineSuccessModel` from `sprix_learning` to update its understanding of agent success rates over time. The router enforces hard authorization constraints by filtering agents based on permissions before evaluating them. It performs a bounded beam search over candidate teams, configurable via parameters like `beam_width` and `assignment_beam_width`. The evaluation logic relies on `sprix_types` for core data structures like `Agent`, `Bid`, `ExecutionState`, `Mode`, and `RouteDecision`. The benchmark suite is split across `benchmark.py`, `benchmark_dynamic.py`, `benchmark_evaluator.py`, and `benchmark_dynamic_evaluator.py`. The held-out evaluators deliberately use different quality, compatibility, cost, and latency equations from SAGE to prevent the comparison from merely crediting SAGE for being the only policy allowed to collaborate. The dynamic benchmark samples completed DAG nodes, concrete artifact portability, sunk resources, and failures to test checkpoint-aware rerouting.

The code quality is high and the tests are thorough. The test suite checks for edge cases like duplicate agent IDs, non-finite requirement weights, and rejecting unselected agent evidence. The CI badge in the README indicates tests run on push, and the repository includes 5 test files. The evaluator logic is carefully separated from the router logic to ensure honest benchmarking. A rough edge I observed was my inline script failing despite the demo and tests passing, which suggests the API might require specific initialization patterns not immediately obvious from the README alone. The state schema version is set to 1, and the library includes logic to serialize and round-trip learned state through JSON, which the tests confirm works.

Developers building A2A agent networks should use Sprix SAGE Router if they need a deterministic, progress-aware way to decide when an incumbent agent should recruit help or hand off a task. It is best suited for systems where tasks have clear DAG dependencies and agents have distinct, measurable skills and permissions. It bites when you try to construct custom inputs without consulting the test suite for the exact data structure expectations, as my inline run showed. However, for its intended use as a research preview and structural routing engine, it runs cleanly and provides clear, explainable routing decisions grounded in observable task progress and agent capabilities.

cd /tmp/rr/wang2122_sprix-sage-router
export PYTHONPATH="$PWD:$PYTHONPATH"

# First, run the demo to confirm the module loads and runs
python demo.py 2>&1 | tail -40
echo "=== DEMO EXIT: $? ==="

# Now run the core SAGE router on a minimal inline input
python - <<'PY'
from sprix_sage import (
    Agent,
    ExecutionOutcome,
    ExecutionState,
    Requirement,
    SAGERouter,
    Task,
)

agents = [
    Agent("planner", {"planning": 0.92, "coding": 0.55}, cost=0.08, latency_ms=900),
    Agent("coder", {"planning": 0.35, "coding": 0.96}, cost=0.12, latency_ms=1200),
    Agent("reviewer", {"planning": 0.60, "coding": 0.88}, cost=0.06, latency_ms=400),
]

task = Task(
    "Implement a REST endpoint that accepts JSON and persists it to Postgres",
    requirements=[Requirement(skill="planning", weight=0.4),
                  Requirement(skill="coding", weight=0.6)],
)

router = SAGERouter(agents, incumbent_id="planner")

print("=== TASK ===")
print(task.description)
print("\n=== AGENTS ===")
for a in agents:
    print(f"  {a.name}: skills={a.skills} cost={a.cost} latency_ms={a.latency_ms}")

decision = router.route(task)
print("\n=== ROUTING DECISION ===")
print(f"  Selected agent: {decision.selected}")
if hasattr(decision, 'reasoning') and decision.reasoning:
    print(f"  Reasoning: {decision.reasoning}")

print("\n=== TRACE ===")
trace = router.last_trace if hasattr(router, 'last_trace') else None
if trace:
    for line in str(trace).split('\n'):
        print(f"  {line}")
else:
    print("  (no trace attribute)")

# Simulate an outcome and feed it back so the learning loop is exercised
outcome = ExecutionOutcome(
    state=ExecutionState.SUCCEEDED,
    agent_id="coder",
    task_id=task.id if hasattr(task, 'id') else "t1",
    cost=0.12,
    latency_ms=1180,
)
print("\n=== FEEDING OUTCOME BACK ===")
print(f"  outcome: {outcome}")
router.update(outcome)
print("  Router updated with outcome (learning loop exercised).")

# Route a second similar task to see if the belief shifted
task2 = Task(
    "Add input validation to the same endpoint",
    requirements=[Requirement(skill="planning", weight=0.3),
                  Requirement(skill="coding", weight=0.7)],
)
decision2 = router.route(task2)
print(f"\n=== SECOND ROUTING DECISION (after learning) ===")
print(f"  Selected agent: {decision2.selected}")

print("\n=== DONE ===")
PY
