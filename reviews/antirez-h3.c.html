I cloned antirez/h3.c and read the source. This is a static code review, not a run, because the repo is C and I had no Apple Silicon Metal toolchain or MiniMax-H3 model snapshot to exercise it. Take the runtime claims here as what the code says, not what I watched it do.

h3.c is a native C inference engine for the MiniMax-H3 multimodal model on Apple Silicon, targeting M3 Max and M5 Max specifically. It handles prompt-to-video and prompt-to-audio generation with first/last frame conditioning and ordered Ref2VA references. The problem is straightforward: run a large multimodal transformer locally on a Mac without a Python runtime or external ML framework. The code is about 25,471 lines of C across 67 files, MIT licensed, with zero test files and no CI.

The architecture is a hand-written DiT pipeline. h3_dit.c at 3,152 lines is the core transformer, with constants for TEXT_DIM 5120, HIDDEN 5376, 56 heads at 128 dimensions each, FFN 14336, 24 video channels, 32 audio channels across 2 streams. It supports int8 quantization on QKV and MLP weights, with flags like int8_mlp, int8_qkv, keep_bf16_qkv, and a set of slower fallback paths for scalar RMS, unfused rope, and grouped quantization. h3_audio_vae.c handles audio decoding with a 7-stage upsampler at 32kHz sample rate, 3 residual blocks with dilation pairs of 1, 3, 5. h3.c itself manages conditioning caches, freeing strings and tensor pointers in h3_conditioning_cache_clear and h3_cache_clear. linenoise.c is vendored for the CLI prompt. Everything is C with pthreads, no external dependencies beyond FFmpeg on PATH.

The code is what you expect from antirez: direct, manual memory management, explicit error paths, a 512-byte global error buffer in h3.c, gpu_op wrapper functions that format failures with operation names. The h3_dit_block struct lists all weight tensors individually including int8 and scale variants, no clever abstractions hiding the layout. There are obvious gaps. Zero test files and no CI mean every change depends on the author running it on actual hardware. The tuning flags like use_slower_row_major_attention_output and use_slower_scalar_qkv_rms suggest performance experimentation left in tree rather than finalized paths. The README mentions M5 Max which does not exist yet, so that detail is aspirational or a typo.

This is for developers who want to read a real Metal inference engine written from scratch in C, not for anyone expecting a working binary without the model weights and a recent Apple Silicon Mac. The int8 quantization paths, audio VAE stages, and conditioning cache are the interesting parts to study. Without tests or CI, and without being able to build it, I cannot say anything about correctness. The code reads clean and deliberate for what that is worth.
