I cloned antirez/h3.c to read the source directly. This is a static code review, not a runtime test. I could not run it because the project is C with no Python entrypoint, and I do not have the Hugging Face model snapshot, Apple Silicon Metal toolchain, or FFmpeg pipeline it requires. What follows is what the source actually shows.

The project is a native C inference engine for MiniMax-H3, a multimodal diffusion transformer that produces video and audio from text prompts, first/last frames, and ordered image or video references. It targets Apple Silicon specifically, using Metal for GPU compute. The README states that prompt-to-video, prompt-to-audio, frame conditioning, and ordered Ref2VA references all work end to end, with current work focused on Metal performance on M3 Max and M5 Max. The core problem it solves is running this large model on a Mac without relying on Python frameworks.

The architecture is a set of hand-written C modules with no external ML dependencies. h3.c is the 1732-line entrypoint that wires together h3_text_encoder, h3_tokenizer, h3_dit, h3_video_vae, h3_audio_vae, h3_video_encoder, h3_vision_encoder, h3_multimodal, and h3_safetensors. It manages a conditioning cache through h3_conditioning_cache_clear and a broader cache through h3_cache_clear, freeing the DiT context, video decoder, and conditioning tensors when keys change or the cache is disabled. h3_dit.c at 3152 lines is the transformer core. It hardcodes model constants as enums: TEXT_DIM 5120, HIDDEN 5376, HEADS 56, HEAD_DIM 128, FFN 14336, VIDEO_PATCH 96, AUDIO_CHANNELS 32, ROPE_FREQS 16, SLOTS 6. The h3_dit_block struct holds fp16 and int8 variants of qkv, attention output, and MLP weights with separate scale tensors, confirming the quantization path is real. A notable design choice is the large set of slower fallback flags like use_slower_row_major_attention_output, use_slower_unfused_int8_inputs, use_slower_scalar_qkv_rms, and use_slower_grouped_quantizer. These let the author keep a known-correct reference path alongside optimized Metal kernels and switch between them for parity testing. h3_audio_vae.c at 1344 lines implements the audio decoder with 7 upsampling stages at rates 5, 5, 2, 2, 2, 2, 2, residual blocks with dilations 1, 3, 5, 32kHz sample rate, and stereo output. linenoise.c provides the interactive REPL.

Code quality is what you expect from antirez: direct C, explicit memory management, no abstraction layers for their own sake. Error handling uses a consistent pattern seen in h3_audio_vae.c where a fail helper formats into a caller-provided buffer and gpu_op wraps each GPU call to propagate errors. The cache teardown in h3.c is thorough, nulling every pointer after free. The int8 and fp16 dual storage in h3_dit_block is cleanly separated. Gaps are real: zero test files, no CI, and 67 files of C with no automated verification. The README mentions vertical slices and parity testing but nothing is codified as a test suite.

This is for developers who want to study or extend a serious Metal inference engine in plain C. It is not a library, not a framework, and not for anyone needing a tested or documented API. It is early, actively changing, and carries the usual risks of a single-author project at this stage. The MIT license and the readable, direct style make it approachable for someone willing to read 25000 lines of C and supply their own model weights.
