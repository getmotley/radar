watermarks-remover is a Python tool that strips AI provenance signals from files. It targets three distinct layers of watermarking. The first is Unicode text hygiene, cleaning up zero-width characters and homoglyphs that some models embed in generated text. The second is statistical rewrite hooks, which rephrase text to break token-distribution watermarks like SynthID. The third is metadata and C2PA removal from PNG, JPEG, WebP, SVG, PDF, DOCX, ODT, HTML, and Markdown. It also exposes an HTTP service so other applications can call the cleaning pipeline over the network instead of running CLI scripts.

The architecture is split into focused modules. `image_meta.py` handles PNG, JPEG, and WebP using only the standard library, scanning for C2PA markers like `c2pa`, `jumb`, and `contentcredentials` in chunk bytes. `container_meta.py` extends this to SVG, PDF, DOCX, and HTML, dropping provenance tags like `xmpmeta` and scanning frontmatter keys including `generator`, `openai`, `anthropic`, and `synthid`. `text_unicode.py` handles the Unicode cleaning layer. `rewrite_text.py` provides an optional paraphrase hook with three backends: a print-prompt default that needs no model, an Ollama integration, and an OpenAI-compatible endpoint. `server.py` wraps everything in a `ThreadingHTTPServer` with endpoints for inspecting and cleaning files sent as base64. The design is stdlib-first throughout. PDF cleaning prefers optional `exiftool` or `c2patool` when present but falls back to best-effort parsing. Security choices are visible in the source: `server.py` binds to loopback by default, enforces a `MAX_BODY_BYTES` cap, supports an optional bearer token, and refuses redirects in the rewrite backend to prevent API keys leaking to unvalidated hosts. `common.py` provides subprocess preexec functions to set resource limits on child processes.

I cloned it, installed it, and its test suite of 16 files passed. Then I tried to run the actual cleaning scripts. I created a text file containing "The quick brown fox jumps over the lazy dog. This is a test of AI generated content detection. Some models embed invisible watermarks in text they produce." and attempted to run `detect_text_watermark.py` and `clean_text.py`. The scripts failed immediately with `python: can't open file '/tmp/service/scripts/detect_text_watermark.py': [Errno 2] No such file or directory` because the working directory resolution was wrong. The fallback attempts also failed with the same path error. I then tried importing the `common` module directly and got `ModuleNotFoundError: No module named 'service'` and `ModuleNotFoundError: No module named 'common'`. The demo script could not execute the core text cleaning because the relative paths in the invocation did not match the repository structure after cloning.

The code quality is uneven. The modules I can read show real thought. The C2PA marker list in `image_meta.py` is specific and covers the actual byte signatures used by the Content Authenticity Initiative. The frontmatter key set in `container_meta.py` is comprehensive, catching both camelCase and hyphenated variants. The HTTP server has proper hardening with input caps, binary-as-text guards, and atomic writes. The rewrite backend correctly blocks redirects and non-loopback endpoints unless explicitly overridden with `WATERMARKS_REWRITE_ALLOW_REMOTE=1`. The maturity signals are decent: 10989 lines, MIT license, 16 test files, and CI enabled. What looks rough is the operational layer. The scripts rely on `sys.path.insert(0, str(Path(__file__).resolve().parent))` to find sibling modules, which works when you run a script directly but breaks when invoked from a different working directory or imported as a package. The path resolution failure I hit suggests the CLI entry points need a cleaner install story, maybe a proper `pyproject.toml` with console scripts.

The verdict is that the core cleaning logic is solid and the module design is careful, but the CLI ergonomics need work. Developers who want to use the HTTP service or import the cleaning functions directly into a larger pipeline will find useful, well-structured code. The C2PA and metadata stripping is the strongest part, the text rewrite hook is a reasonable optional layer that avoids forcing a model dependency. Where it will bite is the command-line experience: running the scripts as documented in the README requires the right working directory, and the lack of a proper package install means you cannot just `pip install` and call `watermarks-remover` from anywhere. Use it if you are building a provenance-stripping service and can wire the modules up yourself. Skip it if you want a polished standalone CLI tool.
